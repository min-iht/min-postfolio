# 노빌드 정적 사이트의 3개 언어 HTML 유지보수 구조

- 날짜: 2026-07-12
- 맥락: Portfolio 저장소에서 min.postfolio-en.html / -jp.html 신규 생성. "ko를 고치면 en/jp도 따로 고쳐야 하는" 유지보수 문제를 빌드 도구 없이 해결해야 했다.
- 태그: i18n, static-site, no-build, vanilla-js, sync-check

## 문제

언어 버전이 3개가 되면 수정 비용이 3배가 될 것처럼 보였다. 하지만 실측(텍스트 인벤토리 조사) 결과, 2,368줄짜리 HTML에서 사용자 가시 한국어는 약 3,200자뿐이고 CSS/JS는 이미 세 페이지가 공유하고 있었다 — 진짜 3벌 부담은 "HTML 구조 변경"과 "공유 JS에 하드코딩된 문구"뿐이었다.

## 시도한 것들 (실패 포함)

1. 단일 HTML + JS 언어 사전(i18n attribute) 방식 검토 → 배포된 2,368줄 페이지 대수술 + 긴 본문 블록(slide_data)이 사전 방식과 안 맞음 + index.html의 3파일 링크 설계와 충돌. 리스크 대비 이득 없어 기각.
2. 템플릿 + 생성 스크립트(경량 SSG) 검토 → 빌드 단계가 생기면 "생성물을 직접 고쳐서 날리는" 사고 경로가 생기고 노빌드 원칙 위반. 기각.
3. en/jp 파일을 통째로 새로 작성(Write) 검토 → 이미지 목록 500여 줄을 재타이핑하면 오타 위험. 기각하고 "복사 후 텍스트만 치환"으로 전환.
4. Edit 도구로 텍스트 80여 곳 수동 치환 → 호출 수가 과다해서, (원문, en, jp, 기대횟수) 4열 대체표를 가진 Python 스크립트 1개로 전환. 이때 "기대 출현 횟수 검증"이 결정적이었다 — 3건이 파일 내 줄바꿈 위치 차이로 매칭 실패한 것을 스크립트가 잡아냈고, 그 3건만 정규식(`re.S`)으로 보정했다.

## 통한 접근법

(1) ko를 정본으로 파일 복사 → 대체표 스크립트로 텍스트만 치환 (구조는 바이트 단위 동일 유지). (2) 공유 JS의 가시 문구는 `{ ko, en, jp }` 객체 + `document.documentElement.lang` 감지(`ko|en|ja` → 데이터 키 매핑)로 전환 — 워크숍 추가가 "한 파일에 번역 3개 넣기"로 줄었다. (3) 구조 지문 스크립트(태그·class·id·data-* 순서 비교, 주석·텍스트 무시)로 세 파일의 구조 동일성을 기계 검증 (`.claude/tools/check_lang_sync.py`).

통한 이유: 이 구조에서 스타일/동작 수정은 원래 1벌(공유 CSS/JS)이고, 텍스트 수정은 본질적으로 언어별 작업(번역)이라 중복이 아니다. 남는 유일한 리스크(구조 드리프트)만 자동 검사로 막으면 된다.

## 일반화된 교훈

1. "N벌 유지보수가 무섭다"는 문제를 만나면, 리팩터링을 논하기 전에 **무엇이 실제로 중복되는지 전수 인벤토리부터** 만들어라 — 공유 자원(CSS/JS)과 본질적 차이(번역)를 빼면 진짜 중복은 대부분 생각보다 작다.
2. 대량 문자열 치환은 Edit 반복이 아니라 **(원문→번역, 기대횟수) 대체표 스크립트**로: 기대횟수 불일치가 곧 "원문이 예상과 다르다"는 자동 경보가 된다. 긴 문장은 파일 내 줄바꿈 위치를 신뢰하지 말고 정규식으로.
3. 구조가 동일해야 하는 파일 쌍이 생기면, 눈이 아니라 **구조 지문(태그·속성 시퀀스) 비교 스크립트**를 만들어 체크리스트에 박아라.
